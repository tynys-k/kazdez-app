# Связанные рабочие процессы KazDez

Репозиторий: `tynys-k/kazdez-app`. Ветка: `codex/erp-connected-workflows`.

## Реализовано в коде

| Запрос | Изменение |
|---|---|
| Задачи | Канбан, поиск, фильтры, смена статуса перетаскиванием и через список; карточка с автором, временем, описанием, ответственными, наблюдателями, правами комментариев, файлами и подзадачами со сроком. |
| Договоры | Отдельный реестр юридических договоров: клиент, номер, даты, организация, сумма, ссылка на Google Диск, файлы, обсуждение. Клиент 360 и абонент открывают конкретный договор. |
| Объекты | Квартира, дом, участок, коммерческий объект; комнаты, площадь, сотки/га, домофон/подъезд; отдельный замер плесени и расчёт фумигации. Фильтр типа объекта в аналитике спроса. Старые записи без типа не объявляются квартирами. |
| Контроль качества | История звонков, автор, время, замечания и оценки в Клиенте 360. Одна позиция очереди на завершённый выезд, а не повторные звонки по одной и той же заявке. «Не ответил» не считается оценкой 5/5. |
| Статусы клиентов | VIP, бережное обращение, госструктуры, постоянный, существующий чёрный список. Автоматический статус постоянного вычисляется по завершённым первичным, порог настраивается, по умолчанию 3. |
| Контакты абонентов | Общая карточка клиента/организации, несколько контактных лиц, должность, телефон, примечание о графике. Абонент связан с клиентом и юридическим договором. |
| Склад | Поставщики и сравнение последних предложений с датами и сроками; склады Байзакова/Мамыр-4 и добавление новых; адресная выдача, перемещение, ревизии; оборудование/СИЗ и происхождение возвратов. Ревизии и передачи у сотрудников проводятся атомарно. Всё находится в «Складе», а не в «Сотрудниках и доступах». |
| Аналитика | План, сезонность, оценки качества и сравнение абонентских/разовых работ перенесены из «Выручки и чека» в «Аналитику». |
| Переплата зарплаты | Перенос указанной суммы из проведённой выплаты в более поздний месяц с основанием. В исходном месяце освобождается перенесённый аванс, в целевом уменьшается остаток к выплате. Деньги по счетам и исходная выплата повторно не меняются. |
| Тендеры | Компактный реестр, раскрытие одного проекта, ответственные/контакты/автор, многократные комментарии, файлы с видом «Подписанный АВР», история изменений работ и обеспечений; связь партнёра с проектами; привязка фактических платежей и контроль возвратов обеспечения; выдача препаратов заказчику с выбранного склада. |

## Перед выпуском — обязательно

Рабочая Supabase **не изменена**. Проверки PostgreSQL выполнялись в локальной PGlite на минимальной схеме (`src/workflows/databaseFixture.js`), не на копии рабочей базы. Это проверяет SQL, транзакции и выбранные права, но не доказывает совместимость с непроверенными ручными изменениями production.

1. Сделать проверяемую резервную копию. Сверить структуру и существующие RLS-политики на staging/копии. В частности, проверить старые таблицы `profiles`, `tasks`, `inventory_adjustments`, `equipment_handouts`, `tender_services`, `tender_guarantees`, `jobs`, `report_chemicals`.
2. Убедиться, что применены предшествующие миграции атомарного создания заявок, закупок, передачи оборудования, контроля качества с исправлением `job_id`, клиентского справочника от 12 сентября, прав доступа и закрытия периодов.
3. Применить новые файлы **в указанном порядке**, не по алфавиту:

   1. `supabase/2026-09-14_connected_workflows.sql`
   2. `supabase/2026-09-14_job_object_measurements.sql`
   3. `supabase/2026-09-14_client_relationships.sql`
   4. `supabase/2026-09-14_multiwarehouse.sql`
   5. `supabase/2026-09-14_employee_stock.sql`
   6. `supabase/2026-09-14_payroll_carryover.sql`
   7. `supabase/2026-09-14_tender_workflows.sql`
   8. `supabase/2026-09-14_tender_deliveries.sql`

   Файлы транзакционные, рассчитаны на однократное применение; повторное применение всех файлов не поддерживается. Вести список успешно применённых миграций. При ошибке остановиться, не продолжать оставшиеся файлы.
4. Проверить staging под администратором, исполнителем, наблюдателем и сотрудником с ограниченными складскими правами: видимость строк и файлов, недоступность чужих задач, комментарии и все операции склада. Проверить одновременные действия двух пользователей: локальный тест не моделирует независимые сетевые сеансы.
5. После успешной проверки выпускать соответствующий интерфейс. Новые таблицы/процедуры требуются для новых функций; выпуск одного интерфейса без миграций не является завершённым внедрением.

## Первоначальное заполнение

- Старый учёт остаётся «Не распределено». Фактические остатки по адресам вводятся после пересчёта и распределения, а не выдумываются миграцией. Новые ревизии сотрудников фиксируют момент пересчёта; старые ревизии сохраняют прежнее правило на конец дня.
- Справочник поставщиков и предложения заполняются настоящими контактами/ценами. Указанные пользователем 17 000/22 000 ₸ не были записаны как подтверждённые закупки.
- Юридические договоры и ссылки на Диск требуют заполнения и явной привязки к клиентам/абонентам. Совпадение названия организации само по себе не создаёт связь.
- Конкретная переплата сотрудника не проводилась: необходимо выбрать исходную выплату, сумму и целевой месяц. Интерфейс не определяет юридическую допустимость удержания и не выполняет банковский перевод.
- Тендерные выплаты связываются с уже проведёнными движениями по счетам; это не новый платёж. После связи изменение суммы исходного движения запрещено. Ошибочные проведённые переносы/связи требуют отдельной проверенной корректировки, кнопка произвольного удаления таких записей не добавлена.
- Файлы хранятся в закрытом bucket `workflow-files`, открываются временной ссылкой; максимум 25 МБ. Старые комментарии, которых не было в базе, не восстанавливаются; для старых дат показывается отсутствие сведений.

## Проверки

- `npm test`: 566 тестов на момент подготовки, в том числе 11 сценариев с PostgreSQL. Проверяются идемпотентность закупок/переносов/выдачи в тендер, права задач, история звонков, привязки договоров, передачи оборудования, ревизия и выдача в один день.
- `npm run lint`: без ошибок.
- `npm run build`: успешно; остаётся предупреждение о крупных пакетах приложения/PDF/Excel.
- `npm audit`: 7 предупреждений в прежних зависимостях Vite/Vitest/ExcelJS и их цепочках, включая high/critical для инструментов разработки. Новый PGlite в отчёте не отмечен. Обновление этих пакетов требует отдельной проверки совместимости; `audit fix --force` не выполнялся. Не открывать dev/test-серверы внешней сети.
- Локальная браузерная проверка использует реальные компоненты с вымышленными данными. `npm run dev` → `/workflow-preview.html`. В этом отдельном dev-входе обращения к данным заменены, реальные операции отключены; в production-сборку он не входит.
- Канбан проверен на 320/768/1024/1440 px: общий горизонтальный выход страницы отсутствует, колонки прокручиваются внутри доски. Проверены фокус и перенос кнопок мобильной карточки, поля участка, расчёт 5 × 4 × 3 = 60 м³, открытие договора и сравнение цен.
- `graphify update .`: граф обновляется без API; SQL-анализатор в окружении не установлен, SQL проверяется отдельными PostgreSQL-тестами.

Полноценные проверки на staging, применение рабочей схемы и публикация приложения — отдельные, ещё не выполненные шаги.
